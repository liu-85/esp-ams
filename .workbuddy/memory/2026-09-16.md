## YAO_AMS：提交即编译 + 单文件一键烧录固件

用户需求：每次提交自动触发编译；编译后发布**一个**可直接烧录到 ESP32-C3 的
BIN 文件，烧完设备即跑，不需要再单独上传 .py/.mpy。

### 核心原理（踩坑记录）

- ESP32-C3 的官方固件是**从 0x0 起的完整镜像**，所以"单文件"= 官方固件
  (0x0) + 自制 littlefs 文件系统镜像拼接到分区表里 `vfs` 的 offset (0x200000)。
- **致命陷阱**：`_boot.py` 启动时 `vfs.mount(bdev, "/")`，`mp_vfs_autodetect`
  靠 block 0 和 block 1 的 **offset 8 处 `"littlefs"` 魔数**识别文件系统。
  挂载失败会走 `inisetup.check_bootsec()`，首扇区非 0xFF 就打印
  "The filesystem appears to be corrupted" 并**死循环**，永远跑不到用户代码。
- 官方 C3 v1.23.0 分区表：nvs@0x9000(24K)、phy_init@0xf000(4K)、
  factory@0x10000(1984K)、vfs@0x200000(2M, subtype **0x81** 但实际是 **littlefs2**，
  不是 FAT)。
- **版本必须对齐**：v1.23.0 内置 littlefs `LFS2_VERSION=0x00020008`(2.8)。
  pip 的 `littlefs-python` 0.19 自带 littlefs **2.11**。最终决定用**设备同源
  2.8.0 上游源码**自己编译工具生成镜像。
- 本地无 gcc → 用 TinyCC 0.9.27 win64 编译 `tools/lfs_mkfs.c` 做本地验证；
  CI 用 ubuntu 自带 gcc。

### 交付物

  `tools/make_firmware_bin.py`（拼装 + 四重校验）、

## YAO_AMS：网页极慢/打不开修复 + 联网策略 + Windows 风格取色器

用户反馈（实机刷固件后）：① 配网能连上但网页打开非常慢、偶尔打不开；
② 第一次配网成功后希望后续不再扫描 WiFi；③ 连不上时 3 次后自动开 AP；
④ 优化网页；⑤ 通道颜色弹窗做成 Windows「颜色」对话框那样。

### 根因定位（网页慢 / 偶尔打不开）

按影响从大到小：

1. **`hanld_rootv2` 逐行发 HTML + 每行 `await sleep_ms(10)`** —— index.html
   400 多行，光发送就 4 秒以上，且每行一个 TCP 小包，还不带 `Content-Length`。
2. **主循环用阻塞的 `wait_msg()`** 收 MQTT —— `umqtt.simple.wait_msg()` 里
   `sock.read(1)` 是阻塞读，没消息时把整个 uasyncio 事件循环按住，
   Web 与状态灯任务全部饿死。这是"偶尔打不开"的元凶。
   → 解法：`check_msg()`（它会把 socket 设非阻塞、read 返回 None；
     `wait_msg` 内部读完后会恢复 blocking=True，所以后续 publish 仍安全）。
3. **`run_web_loop` 里 `await sleep_ms(500)`** —— 每个请求平均多等 250ms。
4. **读请求头 = 阻塞 recv + `settimeout(3.0)`** —— 浏览器会开"预连接"
   套接字却不发数据，服务端卡满 3 秒。
5. **`gc.threshold(1024)`** —— 每分配 1KB 就 GC 一次。
6. **一次页面加载发 5 个请求**（ip/wifi/mqtt/access/hardware），单线程串行。
7. **`get_wifi_info` 每次都 `scan()`** —— 阻塞 ~2 秒。
8. **每 20 轮重连一次 MQTT** —— 每轮都阻塞，实际几秒断一次，非常不稳。
9. **`check_mqtt_connection()` 每次真的发 PINGREQ** —— 状态灯每秒调一次。

### 最终方案

- `network_model.py` 重写：上电**不扫描**，读 `wifi.dat` 直连；
  最多 `WIFI_BOOT_ATTEMPTS=3` 次失败返回 None → 上层开 AP。
  成功判定必须是「关联上 **且** IP ≠ 0.0.0.0」（DHCP 没完成时连 MQTT 必失败）。
  密码错误/找不到 AP 立即返回，不白等。`scan_networks(force)` 带 60 秒缓存。
- `AMS_WEB.py`：index.html 内存缓存 + 一次发完；accept 轮询 20ms；
  `_read_request()` 非阻塞+await 让步，上限 `HEADER_WAIT_MS=600`；
  新增 `/status` 聚合接口；GC 阈值 16KB；favicon 返回 204。
- `bambu_mqtt.py`：`check_mqtt_connection(force=False)` 5 秒节流；
  新增 `poll_msg()`（非阻塞）与 `wait_msg_timeout(ms)`（带超时的换料等待）。
- `AMS_MODEL.py`：`run_ams_loop` 用 `poll_msg()`，只有真收到消息才
  `update_print_info()`（否则会把旧消息反复解析）；重连改
  `RECONNECT_INTERVAL_MS=300000`；查询打印机间隔 `PUSH_INTERVAL_MS=1000`。
- `index.html` 全部重写：Windows 风格取色器 + 手机自适应 + 2 秒轮询。

### 取色器实现要点

- 基本颜色是**程序生成的 6×8**：前 7 列按 `c*360/7` 铺色相 × 6 档明度，
  第 8 列是白→黑灰阶。比手写 48 个色值更整齐。
- SV 区用 CSS 渐变而不是 canvas：
  `linear-gradient(to top, #000, rgba(0,0,0,0)), linear-gradient(to right, #fff, hsl(H,100%,50%))`
- 拖拽用 Pointer 事件 + `touch-action:none`，鼠标/触屏通用。
- 灰色没有色相 → `setFromHex(keepHue)` 保留原色相，体验更顺。
- 输入框回写前判断 `document.activeElement`，避免打字时被覆盖。
- 自定义颜色存 localStorage（16 格，unshift + 去重）。
- `parseColor()` 支持 `#rgb` / `#rrggbb` / `rgb()` / 颜色名（用临时 div 让浏览器算）。

## 二、"接上负载后一直重启 / 电机一直叫 / 网页打不开"

用户报障：刷完固件配好 WiFi 能连网，但接上负载后电机一直有电流声
（一会长鸣、一会间隔响），板子像在反复重启，网页打不开。
硬件：H 桥 **AT8236**，离合驱动 **ULN2803**，用户想把电机 IO 设成 IO2(IN1)/IO3(IN2)。

### 根因（按确定性排序）

1. **GPIO2 / GPIO3 是 ESP32-C3 的 strapping 启动模式脚。**
   依据《ESP32-C3 技术参考手册》第 7 章表 7.2-1：复位释放后由
   **GPIO2、GPIO3、GPIO8、GPIO9** 共同控制 Boot 模式。
   ⚠️ 旧版 `hardware_config.py` 的 strapping 列表只有 2/8/9，**漏了 GPIO3**。
   datasheet 表 4-1 写得很清楚：GPIO2、GPIO8 复位后是**浮空**，
   四个脚里只有 GPIO9 带内部弱上拉。
   → **AT8236 的 IN1/IN2 是"逻辑输入，内置下拉电阻"**（数据手册管脚表原文），
   接上去就把 GPIO2/GPIO3 在上电瞬间拉低，芯片进不了正常启动模式 → 复位循环。

2. **GPIO2 上本来就挂着 1kHz 的状态灯 PWM**（`AMS_WEB.py` 的
   `PWM(Pin(LED_PIN))`，`status_lED()` 里 MQTT 通 → `duty(1000)` 常亮，
   只连 WiFi → 0.5s 亮/0.5s 灭）。IN1 也接 GPIO2 的话，
   电机就跟着状态灯闪 —— **"长鸣 / 间隔响"的规律和状态灯状态一一对应**，
   这是最能一眼确诊的一条。
   另外 `device_processing.huxideng()` 还有一处 `PWM(Pin(2))` 呼吸灯
   （已确认**没有被调用**，属死代码）。

3. 供电：AT8236 的 VM 是 5.5~36V 功率电源，若和 3.3V 共用细线，
   电机启动浪涌会把电源拉塌 → 欠压复位。这类"空载正常、一挂负载就重启"
   是欠压复位的典型特征。

4. AT8236 的限流：`I= VREF/(10*RISEN)`，VREF=2.0V / RISEN=0.2Ω 只有 1A，
   带载会"堵转式"嗡嗡响但不转 —— 也可能被误认为"没启动成功"。

### 改动

- **hardware_config.py**
  - `STRAPPING_PINS = (2, 3, 8, 9)`，补上 GPIO3
  - `SAFE_OUTPUT_PINS = (0, 1, 4, 5, 6, 7, 10)`
  - 电机接 strapping 脚 = **硬错误**；离合/LED 接 strapping 脚 = **警告**
    （ULN2803 输入是达林顿基极，要 1.4V 才导通，空闲时高阻≈悬空，
     而 GPIO2/3/8 官方默认就是浮空，所以能跑但属"带病运行"）
  - 新增 `output_pins()` / `input_pins()` / `validate_detail()` /
    `boot_safety_report()`；`validate()` 仍是 `(ok, problems)`，
    只有错误才让 ok=False（向后兼容）
  - `LED_PIN` 支持 `None`；新增 `MOTOR_BOOT_SETTLE_MS = 200`
  - 电机引脚**保持 GPIO4/GPIO5 不变**（用户想改的 2/3 是本次故障根因）

- **reset_info.py（新模块）**：`capture()` 读 `machine.reset_cause()` 并翻译成
  中文（BROWN_OUT_RESET / WDT_RESET / PWRON_RESET …）、`make_safe()` 上电把
  电机/离合/LED 置到不上电电平、`record_boot()` / `clear_boot_count()`
  写 `boot_stat.json` 记启动次数（数字疯涨 = 复位循环）。
  用 `dir(machine)` 里以 `_RESET` 结尾的名字反查，**不写死数字**。

- **boot.py**：`make_safe() → capture() → record_boot()`，整段包在
  `try/except Exception` 里，绝不挡住 main.py。

- **device_processing.py**：`BOOT_SAFETY` 全局字典（**用 `update()` 原地改，
  不能重新赋值**，否则 AMS_WEB import 到的是旧对象）；
  `build_motor_bus()` 先跑引脚自检打日志，再等 `MOTOR_BOOT_SETTLE_MS` 才挂 H 桥。
  引脚有错**仍然创建硬件**（否则网页都打不开，没法看诊断）。

- **AMS_WEB.py**：`/status` 增加 `reset` + `boot_safety`；新增 `GET /boot_clear`；
  `LED_PIN is None` 时跳过 PWM 且 `status_lED()` 直接 return。

- **index.html**：新增「上电诊断」卡片（复位原因 / 原因说明 / 启动次数 /
  已运行 / 引脚自检 + 重置启动计数按钮）。启动次数 > 5 标红"在反复重启"。

## 18:35 后：AP 能连上但管理页打不开（memory allocation failed, allocating 36096 bytes）

**现象**：刷写固件后能连上 AMS_WIFI 热点，但 `http://192.168.4.1` 打不开；
串口每隔几十毫秒刷一行 `处理请求出错: memory allocation failed, allocating 36096 bytes`。

**根因（已确认）**：`AMS_WEB.hanld_rootv2()` 里 `open("index.html","r").read()`
把 **40KB 的整份页面读成一个字符串**（外加 `send_response` 里 `.encode()` 的第二份拷贝）。
ESP32-C3 空闲堆只有几十 KB 且碎片化，拿不到连续 36~42KB → MemoryError；
更要命的是 `_index_cache` 根本没写进去，于是**每个请求都在同一处再失败一次**，
页面永远打不开。全项目只有这一处大对象分配（grep `.read()` 只有它），
且此前 `gc.collect()` 一次都没调用过。

**修复**：
- `AMS_WEB.send_file()`（新）：`os.stat()[6]` 取长度写 `Content-Length`，
  正文 `open(path,"rb")` 每次只读 `FILE_CHUNK=1024` 字节 → `sendall`，
  块间 `await asyncio.sleep_ms(0)` 让步；发送前 `gc.collect()`。
  单次最大分配从 40KB 降到 1KB，且没有第二份拷贝。
- 删除 `_index_cache`（测试里加了 `hasattr` 断言防复活）。
- 新增 `_raw_send()` 统计本次连接已发字节 + `oom_respond()`：
  **仅当一个字都没发出去时**才补一个极小 503 页面（否则会把半个响应拼坏），
  浏览器不再纯白屏。
- 所有请求异常日志都带上 `mem_note()`（空闲内存 xxx 字节）；
  `/status` 增加 `mem_free`，网页「上电诊断」卡片新增「空闲内存」一行（<20KB 标红）。
- `AMS_MODEL.run_ams_loop`：WiFi 未连接（AP 模式）时不再每 10 秒空转建 MQTT，
  改为退避 30 秒 + 日志降频，串口不再被「未连接wifi」刷屏。

**验证**：
- 测试 54 → **58 项全通过**。关键新测试是**真实功能测试**：
  `_FakeSocket` 假 socket + 真机上那份 42KB 的 `index.html` 实跑
  `hanld_rootv2`，断言逐字节一致、`Content-Length` 正确、

## 刷机后热点起不来 / Web 起不来：四层坑全修完（commit 51ec834）

用户贴串口日志：`RuntimeError: Wifi Unknown Error 0x0101`（板子崩在
`network_model.__init__` 建 WLAN 对象那步），要求上机确认根因并推板验证。

**总根因**：ESP32-C3 上 MicroPython 的 GC **不做压缩**。应用一加载完，
空闲还有 64KB，但**最大连续块只剩 3,584 字节**（`gc.collect()` 只多合出 2KB）。
之后任何"要一大块连续内存"的操作都会失败，失败方式还不一样：
有的抛 `0x0101`（= ESP_ERR_NO_MEM，MicroPython 的 WiFi 错误表只映射
0x3001~0x300E，其它一律显示 "Wifi Unknown Error"），
有的**直接硬复位**——没有 traceback、没有 Guru Meditation，只有 HARD_RESET。

**四层，逐层实测数据（板子串口实测，非推测）**

| 层 | 现象 | 实测 |
| --- | --- | --- |
| 1 | 建 WLAN 对象就 0x0101 | 干净堆 196,992 → 建两对象 172,352（AP 那份 24,576） |
| 2 | 开热点时每 3.3s 硬复位 | 干净堆开 AP 只花 4,176~4,592 字节；加载完应用再开 → 硬复位 |
| 3 | 热点已开，config() 仍 0x0101 | `ap.active()`=True、`ifconfig()` 正常，但 `config(essid/password/authmode)` **任一参数**都 0x0101；`active(True)` 再来一次是 no-op |
| 4 | 扫描/连接 WiFi 会硬复位 | `scan_networks()`/`do_connect()` 里有 `wlan_sta.active(True)`，而 STA 从未在干净堆上开过 |

**修法（一句话）：凡是"要占一大块、且只在启动时做一次"的资源，全部抢在应用加载之前申请。**

- `main.py` 第 0 步：建 AP/STA 两个 WLAN 对象 **并** `sta.active(True)` 真开射频
  （AP 已起时 STA 只花 **48 字节**，驱动共用；零成本换掉运行期所有 `active(True)` 变 no-op）
- 第 0.5 步：`auto_connection()` 失败才 `swcith_ap(1)` 开热点
- 第 0.6 步（新）：`boot_resources.prepare_web_server()` 趁干净堆建好 `:80` 监听 socket
- `network_model.__init__` **不许再 `active(False)`**（继承链会重跑，把刚开好的口关掉）
- `swcith_ap(1)` 改**幂等**：热点已 active 直接返回，绝不再 `config()`
- `AMS_WEB.run_web_loop()` 复用预建 socket，`boot_resources.take_web_server()`

- **`.ps1` 必须纯 ASCII**：WinPS 5.1 把无 BOM 的 UTF-8 脚本按 GBK 解码，
  中文字符串字面量会乱码 → `-match '中文'` 恒为 0（踩过，误以为全是 0）。
  另外注释行以多字节字符结尾时换行会被吃掉，吞掉下一行。
- 推文件用 **base64 分块追加**：`open(f,'wb')` 写第 0 块，之后 `'ab'`。
  **每个分块要逐行 `f.write(ubinascii.a2b_base64("84字符"))`**，
  不要拼成一个 16KB 大字符串再解（实测 `MemoryError: allocating 44032 bytes`）。
- 每文件写完**必须 SHA256 读回比对**，全部 OK 才复位；失败绝不复位（避免半截文件）。
  校验读文件用 2KB 分片 update，别 `read()` 整份。
- 脚本在 `C:\Users\lkfcs\AppData\Local\Temp\`：`push4.ps1`（推+校验+看启动）、
  `bootwatch.ps1`（纯看启动 N 秒）、`probe_*.ps1`（各类单项探测）。

### 探测时踩到的坑（别再踩）

- **`settimeout()` 之后 `connect()` 会报 OSError -203**；不设就正常。
- **自发自收（loopback）测 HTTP 不可靠**：`accept()` 之后 `cli.send()` 会卡死，
  换 `_thread` 跑 main_task 又 `can't create thread`。别再往这条路上花时间，
  真要验网页就**用手机/PC 连 AMS_WIFI 开 http://192.168.4.1**。
- 探测脚本里手动 `gc.collect()` 前别用二分法测最大连续块 —— 分配再释放本身
  就会把堆切碎，导致后面 import 直接 MemoryError（自证预言）。
