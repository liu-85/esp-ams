## 刷机后无 AP：根因确认与修复（延续 09-16 晚 22:30 的串口排查）

- 用户刷的是 CI 固件（release latest = 09e749b「说明」，用户自己 push 的），
  板子起不来热点，串口报 `RuntimeError: Wifi Unknown Error 0x0101`，
  崩在 network_model.py:76 建 WLAN 那一步。
- **根因：0x0101 = ESP_ERR_NO_MEM**（MicroPython 的 WiFi 错误表只认
  0x3001~0x300E，落在外就显示 Unknown Error，非常误导）。
  esp_wifi_init() 要一次性申请约 24KB **连续**堆内存；main.py 先
  `from AMS_WEB import main_task` 把应用加载进堆（吃 ~107KB、切碎堆），
  剩 92KB 空闲也拼不出连续 24KB → 失败。
- **修法**：main.py 顶部、import 应用之前先 `network.WLAN(AP_IF)` +
  `network.WLAN(STA_IF)`。空堆一次成功；之后再调只花 16 字节（对象复用）。
  串口实测：空堆 ~200KB → 成功；WiFi 总代价 AP 24,576B + STA 16B。
- 桌面自测 116/116 过；提交 **6288725**（纯增量，原逻辑原样保留）。
- **板子早上没插**（枚举不到任何串口/CH343）。推板脚本已备好：
  `%TEMP%\push_main.ps1` —— Ctrl-C 抢 REPL → 粘贴模式 base64 写入
  main.py → SHA256 回读校验 → RTS 复位 → 抓 40 秒启动日志 → 自动判定
  （失败关键字 0x0101/Traceback；成功关键字 配置热点已打开/AMS_WIFI/192.168.4.1）。
  板子插上后一条命令完成验证。
- 待办：①板子插上跑 push_main.ps1，确认 AMS_WIFI 出现；②提醒用户 push
  6288725 触发 CI 重编固件（否则下次整烧的还是坏 main.py）。
- 顺手清了根目录临时探针 `_bin_probe.py` / `_boot_sim.py`。
- 串口工具链（都在 %TEMP%，复用价值高）：`mpy_paste.ps1`（粘贴模式执行

## 傍晚：「网页打不开」根因 = C3 内存不够（不是网络问题）+ 双开发板改造

用户强烈反馈：加了 OTA 功能之后网页彻底打不开（之前"只是慢但能用"），
要求「增加 ESP32S3 42 针、同时编译两块板的固件、IO 冲突就拆成两个配置文件、
编译自动调用对应配置、把 S3 剩余可用 IO 全部引出」。

### 1) 「网页打不开」的真正根因（两层，第二层才是致命的）

| 层 | 现象 | 结论 |
|---|---|---|
| 表层 | ESP32 默认 WiFi modem-sleep（`pm=1`），持续传输时周期性休眠 → STA 掉线，串口刷 `ECONNABORTED` | `sta.config(pm=0)` 关掉省电后，空应用下 65KB 页面 5.7 秒发完 |
| **根因** | **C3 只有 400KB SRAM**。不加载应用时空闲堆 149KB；**加载应用后只剩约 60KB**，最大连续块更小。WiFi 驱动收发时要动态申请**连续**缓冲 → 申请不到就 `OSError(113)`，重传 9.4 秒后放弃、射频卡死只能复位 | `probe_sf5`（app 已加载、阻塞式 accept、无 asyncio）仍 `ERR OSError(113) free=60256`；`probe_mem_app` 显示光 `ota_update` 就吃 15968B |

→ 加 OTA 之后应用变大，把「偶发」推成「必然」。**pm=0 是必要的，但在 C3 上
不充分**；真正的解法是换 S3。pm=0 与「发送后 drain 再关连接」两处修复已保留
（对 S3 也有益）。

### 2) 双开发板改造（提交 b361fba，本地提交，未 push）

架构：**同一套业务代码 + 两套引脚表 + 编译期写死板型**

- `python_code/board_c3.py` / `board_s3.py`：只描述"这块芯片哪些脚能用"
  （默认接线 / 保留脚 / strapping / 安全输出脚 / 剩余可用 IO）
- `python_code/hardware_config.py`：只剩「选板型 + 业务参数 + 上电自检」，
  导出所有引脚常量，上层代码一行不改
- 板型优先级：**编译期 `board_select.py`（BOARD="c3"/"s3"/"auto"）** >
  现场 `board_override.py`（可覆盖任意引脚，不进 git）> `os.uname().machine`
  识别（认不出按 C3 并提示）

S3 默认接线：电机 4/5、离合 6/7/8/9（**全干净脚**）、状态灯 2。
C3 上 4 号离合只能挤在 strapping 的 GPIO3（带病运行），S3 没这个问题。
S3 剩余可用 IO **全部列出**：18 只干净脚（含到位开关推荐的 11~14）
+ 4 只空闲 strapping 脚（0/3/45/46）。

构建：
- `python tools/build_mpy.py`（默认 `--board both`）→ `dist/c3/`、`dist/s3/`
  + `dist/esp32c3-ams-mpy.zip`、`dist/esp32s3-ams-mpy.zip`；
  编译时生成 `board_select.py`，**部署说明里直接写出该板实际接线与剩余可用脚**
- `python tools/make_firmware_bin.py --board c3|s3 --chip esp32c3|esp32s3`
  → 暂存源码目录（`dist/_work/src-<board>`）里写入 `board_select.py` 再打包，
  不污染版本库；产物默认 `dist/<芯片>-ams-firmware.bin`
- `python tools/make_update_pack.py --board keep|c3|s3|auto`，默认 keep
  （OTA 只换业务代码，不动设备原有板型设置）
- CI 改成 matrix：C3/S3 各自的 .mpy 包与单文件固件一起构建、一起发布

关键实测数据（已核对）：
- **官方固件分区表**：C3 `vfs @0x200000 size 2MB`（总 4MB）；
  S3 `vfs @0x200000 size 6MB`（**总 8MB → S3 单文件固件必须烧在 8MB 及以上模组**）
- S3 官方固件 `ESP32_GENERIC_S3-20240602-v1.23.0.bin`，
  SHA256 `b91080af2e9b78bad4308f98bb6187567cae24ed77cd7f48ef99b47af3ef0555`
  （C3 那份还是 `8058b7d6…`，没变）

测试：新增 8 项（两份引脚表都校验、板型优先级、S3 剩余 IO 数量）→ **124/124 全绿**。
